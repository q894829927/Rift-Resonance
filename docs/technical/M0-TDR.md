# 《异界共振》M0 技术设计评审（TDR）

> **文档版本：** V1.0 · 2026-10-10  
> **评审结论：** 有条件通过（Conditional Go）  
> **适用基线：** [GDD V1.0](../GDD.md)  
> **性质：** 技术方案评审与 M0 实施规范；**不代表代码已经实现或通过测试**。  
> **目标环境：** 本地 Windows 开发优先；后续验证阿里云 ECS（2 vCPU / 2 GiB / 40 GiB，Alibaba Cloud Linux 4）。

## 1. 评审范围、边界与最终决定

M0 的单一目标：**在浏览器中让两个玩家通过同一台权威服务端进入房间、移动，并看到一致且平滑的位置结果**。以可执行的最小联机垂直验证闭环，为后续战斗系统提供稳定边界。

**M0 包含：**
- 前后端及共享包的工程组织；
- 浏览器 Phaser 画面（占位图即可）与键盘八方向输入；
- Colyseus 房间创建/加入及玩家生命周期；
- 固定时间步、服务器权威移动、同步状态；
- 本地输入预测/校正、远端玩家插值的最小验证；
- 最小断连提示、日志、延迟和资源使用观测；
- 本地双客户端自动/人工验收，ECS 的可选部署烟测。

**M0 不包含：** 自动攻击、怪物 AI、碰撞伤害、升级、共振、复杂地图、邀请码业务、完整掉线重连、数据库、排行榜、移动端操作与正式公网运营。将这些提前塞进 M0 会干扰网络架构验证。

**已确认的决定：**

| 编号 | 决策 | 状态 |
|---|---|---|
| ADR-001 | 客户端使用 Phaser + TypeScript；服务端使用 Node.js + Colyseus | 接受 |
| ADR-002 | **模拟层独立于** Phaser、Colyseus、网络和操作系统 API | 接受，M0 必须 |
| ADR-003 | 单服务器实例、单进程、每房间独立世界；不引入 Redis/K8s | 接受 |
| ADR-004 | 服务端固定模拟 20 Hz，网络状态补丁 10 Hz，渲染目标 60 FPS | 接受为可调基准 |
| ADR-005 | 客户端上报**输入意图**而非坐标/血量；服务器拥有最终状态 | 接受，M0 必须 |
| ADR-006 | 优先评估 Colyseus **0.18+** 官方预测/校正 API；实际版本锁定后再实施 | 条件通过 |
| ADR-007 | Room State 为客户端需要的**网络投影**，不直接充当完整战斗世界模型 | 接受，M0 必须 |
| ADR-008 | 战斗表现与网络事件解耦；临时效果不用永久 Schema 状态同步 | 接受 |
| ADR-009 | M0 先本地验证，ECS 环境与公网发布独立验收 | 接受 |

> 框架注意事项：Colyseus 官方文档在 0.18+ 提供 `defineInput`、`setFixedTimestep`、`room.input()`、`Predict` 等 Netcode API；旧版本教程中的 `setSimulationInterval` 或自行处理的输入回执不能直接与新版流程拼接。正式实施前必须记录锁定版本并运行最小兼容性验证。

## 2. P0 / P1 发现与处理建议

### P0-01：完整世界状态和网络 Schema 边界未定义

**问题：** GDD 只描述了“服务器算、客户端显示”，未定义战斗世界状态与广播数据如何隔离。一旦让 `Room.state` 直接承载整套战斗逻辑，未来 60 只怪物、120 个逻辑弹丸与状态效果将导致耦合及序列化成本上升。

**决议：** `Simulation.World` 为权威计算模型；`NetworkProjection` 选择需要同步的属性；`Colyseus Room.state` 仅承载面向客户端的状态快照/增量。Room 负责生命周期和桥接，不实现具体移动或战斗规则。

**验收：** 模拟层可在 Node 单元测试中运行，不依赖 Phaser、Colyseus 或 DOM。

### P0-02：固定步长、输入、补丁频率之间缺少协议契约

**问题：** 20 Hz 模拟、10 Hz 同步和客户端 60 FPS 是三个独立频率，不能让客户端每帧发送输入或让渲染帧时间直接推进服务端世界。

**决议：** M0 以 50 ms 的固定逻辑步长推进；客户端按照相同输入 Tick 采样；状态每约 100 ms 向客户端发送增量；渲染按独立帧率插值。Colyseus 0.18+ 优先使用官方固定时间步与预测工具，而不是复制一套自定义不兼容的 Tick/ACK 实现。

**验收：** 降低浏览器 FPS 不应改变服务器上按时间运行的权威移动速度；连续输入、斜向移动与断连停止输入符合定义。

### P0-03：没有定义客户端输入的合法范围与时序

**决议：** M0 仅允许离散移动输入 `moveX` / `moveY`，范围分别为 `-1, 0, 1`。服务端规范化斜向移动，拒绝非法值；由框架记录顺序及消费状态，不相信客户端的坐标、速度、时间戳、伤害或任意玩家标识。未来冲刺/技能须单独定义边沿触发语义，不能每帧重复执行。

### P0-04：协议和运行环境尚未版本固定

**决议：** 选定兼容的一组 Phaser、Colyseus、SDK、Schema、Node.js LTS、TypeScript 版本，固定 lockfile，并通过一个最小双人房间测试再升级依赖。不能因为文档中有 0.18 API，就假定任何 Colyseus 安装版本都支持。

### P0-05：部署前置条件未独立界定

**问题：** 当前 ECS 曾处于无公网 IP / 0 Mbps 状态；Workbench 能访问 ECS 不代表浏览器已可通过公网连接游戏。

**决议：** M0 在本机/局域网验证即可；公网 IP、WSS、HTTPS、备案和带宽变更作为部署门槛单列。开发时禁止把无鉴权的 Colyseus 管理接口直接暴露公网。

### P1-01：升级次数与构筑容量存在潜在冲突

GDD 设计在 Boss 前约 9 次升级，但理论上完成“解锁第二武器 1 次 + 两武器分别升至 III 共 4 次 + 三个被动各解锁 1 次 + 进化 1 次”恰好耗尽 9 次，无法再升级被动至 II 级。

**建议在 M3 前解决**：调整升级次数、专设武器成长通道或提高升级的组合收益；M0 不擅自修改 GDD 数值。

### P1-02：共振伤害队列边界需提前预留

未来共振规则需要稳定的事件 ID、来源玩家、技能标签、反应冷却以及“反应伤害不再触发反应”的标志。M0 仅确立模块边界，不进入正式共振实现。

### P1-03：性能和网络指标仍是设计假设

GDD 中的“单房间 20～60 KB/s”“Tick P95 < 25 ms”等属于待验证指标，不能当作实测承载结果。M0 需要具备采集接口；怪潮压力测试安排到 M1/M5。

**依赖方向（不可反向）：**
- `apps/client` → `packages/shared`；预测移动可以使用 `packages/simulation` 中纯函数；
- `apps/server` → `packages/shared`、`packages/simulation`；
- `packages/simulation` → `packages/shared`，不得依赖 `apps/*`、Phaser、Colyseus、Node 网络服务；
- `Room` 可以调用模拟，但模拟内部绝不能调用 `Room.broadcast()`；
- Phaser 场景不可以修改服务器 Schema 来提交玩家位置。

早期不引入 ECS 框架、复杂 DI 容器、Redis、数据库和多进程服务架构。

## 4. 游戏循环与状态所有权

### 4.1 服务端权威循环

每个房间一个独立的 `World`，使用固定时间步。推荐时序：

1. 接收和缓存输入（经范围校验）。
2. 固定 Tick 开始，确定本 Tick 使用的输入。
3. 玩家移动：归一化方向 × 速度 × 固定 `dt`。
4. 更新位置与简化世界边界。
5. 输出权威玩家状态。
6. 将 World 中需要同步的数据写入网络投影。
7. 按 Colyseus 的补丁频率向客户端同步改变。
8. 记录 Tick 时间、状态数量、网络发包量等遥测。

M0 使用简单矩形活动区域，不引入复杂物理引擎。坐标系单位为像素，`dt` 单位为秒。严格限制一个输入步的最大位移；斜向单位方向必须规范化。

**时间基准：** 服务端以固定 `serverTick` 维护战斗逻辑时间；日志中的墙钟时间只用于诊断、网络测量、连接超时，不直接作为战斗计算的确定性输入。未来 RNG 采用显式种子，不直接从场景对象或 `Math.random()` 随意取值。

### 4.2 客户端显示循环

- 每渲染帧读取本地玩家预测位置；与服务器状态比较并校正；
- 对远端玩家缓存最近的服务端状态并平滑插值（建议从约 100 ms 插值延迟起测）；
- 插值结果仅用于显示，不反写到权威世界；
- 如果连接丢失，提示重连中或连接已断开，停止向过期房间发送新输入；
- Phaser 渲染 FPS 波动不得决定客户端网络输入 Tick 数量。

M0 先用两种不同颜色的方块/简易角色测试，不将美术与光效纳入评审关键路径。

## 5. M0 网络协议最小契约

下表是**语义契约**，不是要求立刻自定义二进制网络栈。对于 Colyseus 0.18+，输入 Sequence/ACK 由官方 `room.input()` / `Predict` 链路管理，应用层不得重复发明一套不同步的 ACK。

| 通道 | 方向 | 字段/语义 | 拒绝条件 |
|---|---|---|---|
| Join / Create | 客户端 → 服务端 | 昵称（长度限制）、房间选择 | 非法长度、房间不可用 |
| MoveInput | 客户端 → 服务端 | `moveX, moveY` ∈ {-1,0,1} | 非法类型、越界、未入房 |
| RoomState | 服务端 → 客户端 | `phase`, `serverTick`, `players` | 只读 |
| PlayerState | 服务端 → 客户端 | `sessionId`, `x`, `y`, `connected` | 只读 |
| ConnectionStatus | 连接生命周期 | joined / dropped / left / error | 客户端只显示，不据此修改权威世界 |
| Diagnostics | 本地测试工具 | RTT、Tick 时间、收发字节 | 不开放为公网管理接口 |

建议状态示意：

- `RoomState.phase`：`LOBBY | PLAYING | ENDED`；M0 只用 `LOBBY | PLAYING`。
- `RoomState.serverTick`：单调递增的 Tick 计数。
- `RoomState.players`：用不可由客户端伪造的会话标识关联玩家。
- `PlayerState.x/y`：服务端权威位置；初版浮点数，后续再评估定点量化。
- `PlayerState.connected`：供其他玩家显示在线状态。

**数据分类规则：**
- 长期持续且客户端必须知道的状态，使用 Colyseus Schema 增量同步；
- 开始游戏、结算、技能发射、共振提示等一次性事件，在后续阶段使用消息/事件；
- 仅供服务端战斗判定的私有字段，不写入通用网络 Schema；
- 历史输入缓存、服务器连接对象、内部定时器与调试对象不得进入 Schema。

## 6. 版本策略与可测试性

推荐在 M0 首次实现前记录：

- Node.js 当前受支持的 LTS 主版本；
- 与该 Node 版本兼容的 Colyseus（优先 0.18+）、SDK 与 Schema；
- Phaser、TypeScript、Vite 版本；
- 包管理器版本与锁文件；
- 本地开发命令、单元测试命令、构建命令。

版本选择遵循**同一套 SDK 与服务端文档**，不混用旧版本 `@type()` 示例、旧重连生命周期和新版 `Predict` 流程。

**M0 必需测试：**

| 测试编号 | 条件 | 通过标准 |
|---|---|---|
| T-01 | 服务端与两名客户端启动 | 两人加入同房间，ID 不同，互相可见 |
| T-02 | 仅客户端 A 按 W/A/S/D | A 由服务端推进，B 观察到位置同步 |
| T-03 | 45° 斜向移动 | 单位时间移动距离不超过同速直线移动 |
| T-04 | 客户端停止移动 | 服务端停止持续移动，不出现无限惯性 |
| T-05 | 修改客户端本地显示坐标 | 不会直接修改服务器权威坐标 |
| T-06 | 客户端 FPS 降低到约 20 | 服务端移动速度不跟随 FPS 变慢 |
| T-07 | 模拟约 80/150 ms RTT | 可操控，远端移动平滑，无永久位置漂移 |
| T-08 | 非法输入（NaN/越界/伪造其他玩家） | 服务端拒绝或规范化，不破坏世界 |
| T-09 | 一名玩家连接中断 | 其他玩家继续运行，显示断连状态 |
| T-10 | 连续运行 15～30 分钟 | 无持续增长的资源泄漏或未处理异常 |
| T-11 | 相同初始位置与输入序列 | 模拟层的最终位置在确定精度内一致 |
| T-12 | 框架版本/依赖锁定 | 全新环境能完成安装、构建与最小双客户端验收 |

> 本评审仅定义 T-01～T-12；**尚未执行任何测试**。M0 的正式完成必须提供日志、截图或自动测试记录，不能仅依据代码存在判定完成。

## 7. ECS 部署与性能验证门槛

### 7.1 分两阶段

**阶段 A：本地**  
同一台 Windows 电脑开启两个浏览器窗口分别连接本地 Node 服务。之后用局域网内的第二台设备验证连接与延迟。无需公网 IP，也不会因测试窗口往返包而产生 ECS 公网流量。

**阶段 B：ECS 烟测（M0 后段或 M5 继续）**  
先测机器是否支持受选版本的 Node，记录 `free -h`、CPU 型号及运行内存；确认服务端正常启动并通过健康检查。若需要真正跨公网访问，另行确认公网 IP、带宽/流量计费、HTTPS/WSS、安全组及合规要求，不把此项与本地 M0 功能混为一谈。

### 7.2 资源目标（尚未实测）

- M0 单房间/两客户端测试时，服务端进程 RSS 建议控制在 300 MiB 以内作为观察目标，若超标必须分析而非立即宣告失败；
- 记录 20 Hz Tick 的平均、P95、P99 耗时；
- 记录每名客户端每秒出站字节、房间总出站字节；
- 预留系统及 Web 服务所需内存，避免 2 GiB 实例直接 OOM；
- 本地先只跑一个服务端进程，不默认开启多个 Node Worker 或 Cluster；
- 上线前对 WSS 使用 TLS 终止，游戏进程仅监听本地或受保护接口；
- 严禁以 root 身份运行公开游戏服务。

这些是**预算与检验要求**，不是这台 ECS 已经证明能够承载 4 人房间的事实。

## 8. M0 开发工作包与依赖顺序

| 步骤 | 工作包 | 完成定义 |
|---|---|---|
| M0-A | 初始化 monorepo、版本锁定、开发脚本 | 新环境能安装、启动、构建 |
| M0-B | 房间、玩家标识、Schema 投影 | 两客户端入房并互相看到两个实体 |
| M0-C | 独立 Simulation 与固定移动 Tick | 无渲染纯测试能重放相同输入 |
| M0-D | 输入通道与服务端消费 | 玩家仅能通过输入指令移动 |
| M0-E | 本地预测、服务端校正、远端插值 | 网络延迟下移动具可接受的平滑性 |
| M0-F | 联机与异常测试、遥测 | T-01～T-12 取得可复核结果 |
| M0-G（可选） | ECS 单进程烟测 | 实际内存、CPU、网络路径得到记录 |

**建议顺序：** 先完成 B/C/D 的纯权威移动，再增加 E，不要一开始同时调试预测、同步、角色动画和复杂场景。

## 9. 进入 M1 的质量门禁（Go / No-Go）

可进入 M1 的条件：

1. T-01～T-12 中与 M0 核心范围有关的项目全部有通过证据；ECS 公网相关项目可以标记为明确的后续阻塞，而不妨碍本地战斗开发。
2. 服务端模拟代码不依赖 Phaser 或 Colyseus 的场景对象。
3. 所有权威状态变更发生在服务端的统一 Tick 流程内，Room 不直接编写游戏规则。
4. 客户端不能通过提交坐标或伪造玩家 ID 修改其他玩家位置。
5. 客户端渲染与同步频率解耦，出现临时延迟时没有永久位置漂移。
6. 最小联机测试能重复运行，产生基本日志和资源记录。
7. 模型/网络协议、包版本和命令文档已经固化并提交仓库。

**若未满足：** 留在 M0 修复；不因为两个人在浏览器里能看到方块就直接宣告联机架构完成。
