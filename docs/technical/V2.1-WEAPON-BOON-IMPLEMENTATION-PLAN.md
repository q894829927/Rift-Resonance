## 3. 核心数据模型（逻辑设计，非最终 TypeScript 定义）

**玩家构筑：**

```ts
interface CombatBuildState {
  weaponIds: WeaponId[];             // 最多 2
  weaponLevels: Map<WeaponId, 1|2|3>;
  weaponBranches: Map<WeaponId, BranchId>; // 每武器最多 1
  resonanceBoons: Set<ResonanceBoonId>;    // V2 先最多 1
  passiveLevels: Map<PassiveId, number>;   // 原有 3 槽限制
}
```

**场上交互对象：**

```ts
interface CombatAreaEffect {
  id: string;
  kind: "ember" | "frost_zone" | "gravity_field" | "spatial_anchor" | "conductive_node" | "steam_zone";
  ownerPlayerId: string;
  originWeaponId: WeaponId;
  x: number; y: number;
  radius: number;
  createdCombatTick: number;
  expireCombatTick: number;
  charges: number;
  flags: number;
}
```

**冰晶晶簇等附着状态：** 放入目标 status 表，不生成不必要的独立空间实体。`originPlayerId`、`lastAppliedCombatTick`、状态层数、到期时间和已消耗标识必须可确定地计算。

**服务端攻击结果**分两种：
1. `DirectHit`: 原生武器/场域合法直接命中，可触发一次基础交互或契约。
2. `SecondaryHit`: 共振、额外分裂、弹射的二次伤害，按明确白名单允许贡献经验，但**默认不得递归触发新的高级契约**。

为避免混淆，高频范围伤害可批量结算，最终经过既有 `DamageSystem.applyEnemyDamage`，由其统一处理防御、去重、死亡与经验。

**时间基础：** 仅在 RUNNING 增加的 `matchElapsedTicks` 用于效果寿命、触发冷却；`world.tick` 用于同步 Tick 与升级倒计时。不得因升级暂停而使火种和引力场提前过期。

## 4. 单帧确定性运行顺序

延续现有 `world.ts` 的固定 20Hz Tick，在 RUNNING 内按以下阶段更新：

1. 验证、应用玩家移动/冲刺输入；更新当前玩家位置。
2. 刷新敌群并推进基础敌人 AI/冲锋运动。
3. 应用状态限制及有效引力牵引（同敌人选唯一牵引源；与冲锋免疫规则兼容）。
4. 执行武器发射与持续攻击触发。
5. 推进实际伤害弹丸/即时闪电/法环接触命中。
6. 更新火种、寒霜、引力、锚点等场域；处理到期与坍缩（到期效果在出队前完成合法结算）。
7. 收集和排序基础交互/高级共振候选，只执行一层高级反应；本 Tick 消耗对象按稳定键排序。
8. 通过统一伤害入口提交伤害、击杀、XP 和多人贡献。
9. 清理到期/死亡目标挂载状态；检查升级和胜负；生成有唯一 ID 的核心表现事件。

**注意：** 当前敌人 AI 在武器和伤害之前处理；移动与引力作用的位置及优先级必须通过集成测试验证，必要时把效果计算拆为“作用移动”和“处理到期伤害”两阶段，不能让同一敌人在一次 Tick 被牵引两次。

**反应防递归：** 不使用任意嵌套的 `onHit` 回调产生另一轮 `onHit`。采用事件任务队列：直接命中 → 基础交互 → 最多一次高级契约 → 标记 `secondary` 的附加伤害。每事件目标数和每 Tick 总处理数有上限。

## 5. 升级与双重祝福获取实现

新增升级类型：`weapon_unlock`, `weapon_branch`, `branch_power`, `passive`, `resonance_boon`（可保留旧 `weapon_power` 作 V1 兼容）。

必须验证：

- 新武器不超过 2 槽；重复武器无效。
- I 级武器升级到 II 时，必须同时选择合法的一个分支，写入不可修改的分支 ID。
- 只有选定分支才可升级 III；一个武器不能同时拥有 A/B 分支。
- 只有同一玩家具备两条指定 II 级分支，才允许获得对应双重祝福。
- 个人持有双重祝福最多一个；不能用其他玩家持有的分支借用前置条件。
- 祝福生效时能合法消耗队友创造的战场对象。
- 4 分钟可玩模式至少要提供获取第一个契约所需的 4 次升级；设计独立的 XP 节奏/构筑保底配置，不用后台偷偷授予卡片。
- 开发版构筑预设与正式匹配环境隔离，支持固定种子复现但不能被普通客户端调用。
- 重抽与超时选择重复校验服务器候选 ID，禁止客户端伪造选择/注入任意分支。
- 一次重抽保留此前的确定性 RNG，所有追加的权重抽取必须能由种子和操作顺序完整回放。

**合法性检查集中在服务端。** UI 只显示可选卡片、下一等级/前置条件与未来可能解锁的契约，不计算实际权限。

## 6. 网络投影、事件与表现

### 6.1 最小同步

- 玩家：原 `weaponIds/weaponLevels` 外，加 `weaponBranches` 和 `resonanceBoons`（原型可以用 JSON 字符串，后续按变更频率评估 Schema 优化）。
- 场域：同步 `id, kind, owner, x, y, radius, expireCombatTick, 主要状态`，对持续可见/可交互领域采用有上限的 Schema map；无伤害的粒子留在客户端。
- 瞬时共振：服务端发布稳定唯一 ID 的 `resonance.triggered` 等事件，包含来源玩家、领域 ID、位置、效果 ID、强度和必要随机种子；客户端不得据特效反推伤害。
- 既有 `CombatEvent` 字段不足以表达多目标/多协作者时，应增明确的可选字段或紧凑扩展，不能把多个意义塞进一个 `amount`。
- 网络协议字段发生兼容性破坏时升级 `PROTOCOL_VERSION` 并明确拒绝旧客户端，而不是让新旧客户端静默不同步。

### 6.2 事件容量

当前 `COMBAT_MAX_EVENTS = 64`，快速群伤时可能出现一帧/两次同步间高频事件挤占主要技能事件。应做真实事件压力测试，采用**优先保留核心反应事件、合并/降采样装饰伤害事件、批量局部表现**的方案；绝不能因事件队列已满而丢失实际服务器伤害结算或生成重复伤害。

### 6.3 Phaser 表现

- 每类武器和区域创建独立 renderer adapter，`main.ts` 只调用 `create/update/destroy`。
- 位置插值沿用已完成的射弹平滑框架；静止领域靠服务端存续状态渲染，不按每帧任意重建。
- 火种吸入、坍缩、节点导电线可用轻量程序化 Graphics/粒子完成；不需要每粒子都与服务器同步。
- 给危险预警更高的视觉优先级；共振大型特效不得盖住玩家受击、冲锋锁定提示。

## 7. 分阶段实施任务（每阶段可独立验收）

### T0｜规格、基线与迁移安全（先做）

- 添加新的 V2.1 规则文档；梳理 V1 vs V2 差异。
- 固定旧版构筑与联机测试基线。

- V2 正式武器池中不再掉落回旋刃，但旧逻辑与测试仍可运行。

**验收：** 现有构建/单元/集成测试全绿；legacy 玩法完整可重演。

### T1｜武器注册表、分支状态与升级骨架

- `WeaponId/BranchId/BoonId` 稳定枚举与规格注册；从当前 `if (fireball)/else if (spin_blade)` 逐步迁移。
- `CombatPlayer` 增分支与祝福存储；reset/new match/断线重连投影同步。
- 升级池支持两武器、II 选支、III 强化、合法契约、一次重抽与强制/保底候选。
- 定义 4 分钟独立 XP 原型配置并写调试数据工具。

**验收：** 2 槽/单分支/1 契约的属性测试；固定 RNG 可重演；任何伪造非法选项被拒绝。

### T2｜通用区域对象和状态交互基础

- 实现 `areaSystem`，支持有上限的 `ember`、`gravity_field`，管理创建/消耗/到期。
- 实现同 Tick 最大一个有效引力源、Boss 位移免疫、精英削弱、地图边界、敌群集聚规则。
- `resonanceSystem` 只消费合法直接命中与对象事件，带稳定事件 ID 和二次反应抑制。
- 先提供简单可读的火种/引力圈，无需正式美术。

**验收：** 暂停不失效、同时重叠不双倍拉扯、重复消费不能重复伤害、离房/重开清理一致。

### T3｜首个纵向切片：火焰弹 + 虚空法球 + 坍缩爆炎

- 火焰弹 II `ember`、III 分支强化；虚空法球 I 与 II `collapse`、III 分支强化。
- 攻击落点、火种收集、场域到期坍缩、最多 3 火种的高级融合。
- 保证没有契约时单把火焰弹/虚空法球仍有有效输出；跨玩家火种可被合法消耗。
- 加入服务器共振事件与客户端橙紫火焰坍缩演出。

**验收：** 1p/2p、4 分钟对局至少能构筑出第一契约；重复/到期/边缘/高延迟无重复爆燃或漏清理；保留原有火球平滑移动。

### T4｜第二纵向切片：穿透箭 + 静电链 + 雷霆矩阵

- 直线扫掠穿透箭；静电链即时目标/节点弹射；导电节点稳定 ID 与有效期。
- 箭 II `nail`、电 II `arc`；III 扩展；契约 `thunder_matrix`。
- 相同节点每次反应只能通过一次；多个玩家的节点/闪电混合触发。
- 增加放射状电弧和网络表现，避免每段装饰性电流都成为高频服务器弹体。

**验收：** 1p/2p 完整触发，确定性节点遍历，无无限传导；非契约玩法保持独立价值。

### T5｜补完四武器的各自第二分支 + 组合节奏调优

- 完成 `fireball.split`、`void_orb.anchor`、`piercing_arrow.volley`、`chain_lightning.thunder_core`。
- 确保没有专属双重祝福时分支依旧能清怪；留出 `curvature_rain` 后续接口。
- 新升级卡说明升级后行为与潜在组合；测量玩家首契约时间和构筑有效率。

**验收：** 四把武器共 8 分支行为存在明显差异；任意组合不死锁、不越槽；普通玩家可自然完成一套构筑。

### T6｜剩余两武器和完整六种核心契约

- 修订分支图上没有候选祝福的情况（`curvature_rain`、`steam_field` 作为候选留接口，是否第一版发布单独评审）。

**验收：** 六武器 12 分支，至少 6 核心契约可被合法获取；所有 12 分支至少有“独立完整攻击循环”，不能把候选祝福作为生存必需品。

### T7｜十二分钟模式与性能平衡（后置）

- 9 次左右升级的成长曲线、2–4 人缩放、精英/Boss 抗性、传奇祝福评审。
- 视觉层级和高密度命中特效降级；ECS CPU、带宽与内存测试。
- 专门检查虚空法球选择率和带宽/性能；避免成为团队必选。

**验收：** 完整 12 分钟对局稳定，可至少复现三类机制差异显著的构筑；无带宽/事件洪峰造成伤害不同步。

## 8. 自动化验收清单

### 8.1 规则单测

- 槽位上限：2 武器、3 被动槽、1 契约；分支互斥与 II→III 合法。
- 契约前置：对 8 组配方进行正反例及假输入测试；III 非必需。
- 相同种子、相同输入和候选：升级、重抽、超时自动选择结果完全一致。
- 火球每次命中生成火星且不无限分裂；杀敌追加只加有限数。
- 引力源择优/上限/强敌豁免/边界；火种仅消费一次；来源玩家清楚。
- 同 Tick 多人触发竞争同一对象时，固定排序结果可重演。
- UPGRADING 冻结战斗时钟，领域不自然过期；战斗恢复时间继续。
- 次级伤害不递归触发高阶反应；死亡经验只结算一次。

### 8.2 集成测试

- 单人、双人、四人：武器获取、升级阶段、契约激活、共振伤害与归属。
- 网络 10Hz 投影与重复/迟到事件：客户端去重、事件丢失策略、火种与引力场一致性。
- 玩家死亡、掉线、回房、重新开局；服务器实体和客户端装饰同时清理。
- 目标提前死亡、多人同时打同目标、两领域同 Tick 重叠、法环弹体多次穿越。
- 跨规则版本（legacy 与 V2）客户端协议识别并拒绝危险不兼容操作。

### 8.3 性能测试

- 玩家 1/2/4，怪物数 20/40/60，多层火种+引力+大量弹射压力情况。
- 记录 Tick p50/p95/p99、各阶段耗时、范围查询总次数、活跃区域数、事件生成/丢弃数。
- 记录网络每秒收发字节与 60FPS 下客户端渲染帧时间；核心共振事件不得被装饰消息挤掉。
- 以 ECS 2vCPU/2GiB 目标环境进行复测；没有真实测量之前不能声称达标。

## 9. 发布与回退策略

- 原型新玩法使用独立开发分支和清楚的 ruleset 标记；不直接覆盖稳定联机流程。
- 每阶段优先合并小范围可回退的功能；旧回旋刃实现先保留可运行，不在引入虚空法球时删测试。
- 对 Schema 改动同时更新服务端投影、客户端类型与兼容判断，不滚动部署混用破坏性版本。
- 新玩法验证失败时可切回 legacy 规则，避免用户当前已完成的开发成果失效。

## 10. 开发前仍须记录的可调参数

- 6 把武器与 12 条分支的伤害/冷却、触发频率、持续时间。
- 引力领域牵引优先级、精英抗性、场域数量和主动目标上限。
- 各契约具体增幅、范围、触发周期、跨玩家收益。
- 四分钟升级经验曲线与构筑保底权重。
- 反应每 Tick 上限、每秒网络事件预算、客户端特效分级。

**建议执行顺序：T0 → T1 → T2 → T3（第一套完整可玩构筑）→ T4（第二套对比构筑）→ T5 → T6 → T7。**
